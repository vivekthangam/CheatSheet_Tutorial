# Layer 1: Symmetric AEAD & The Nonce/IV Reuse Catastrophe

### Scenario 1: Why Reusing an IV/Nonce in AES-GCM is a Fatal Cryptographic Catastrophe
**Interviewer Evaluation:** Assesses mathematical understanding of Galois Counter Mode (GCM), GHASH authentication key recovery ($H = E_K(0)$), plaintext XOR leakage, and authenticated encryption (AEAD).

#### Technical Deep Dive
AES-GCM combines Counter (CTR) mode encryption with Galois Message Authentication Code (GMAC):
1. **The Plaintext XOR Leakage**:
   - In CTR mode, keystream is generated by encrypting the nonce and incrementing counter: $S_i = E_K(\text{Nonce} \parallel i)$.
   - Ciphertext is: $C_1 = P_1 \oplus S$ and $C_2 = P_2 \oplus S$.
   - If two different messages are encrypted with the **exact same Key and Nonce**:
     $$C_1 \oplus C_2 = (P_1 \oplus S) \oplus (P_2 \oplus S) = P_1 \oplus P_2$$
   - The keystream $S$ cancels out completely! If an attacker knows or guesses $P_1$, they compute $P_2 = (C_1 \oplus C_2) \oplus P_1$ trivially.
2. **The GHASH Authentication Key Compromise**:
   - GCM uses a polynomial evaluation over the Galois field $\text{GF}(2^{128})$ parameterized by hash key $H = E_K(0^{128})$.
   - With two ciphertexts using the same nonce, the difference of authentication tags yields a polynomial whose roots reveal the internal **GHASH key $H$**!
   - Once $H$ is known, the attacker can forge valid authentication tags for arbitrary forged messages without knowing the secret AES key!
- **Rule of Thumb**: For AES-GCM, **NEVER use static IVs**. Generate a cryptographically random **12-byte (96-bit) IV** for every single encryption operation using `SecureRandom`. Prepend the 12-byte IV to the ciphertext output.

```java
// Production-Grade AES-256-GCM Encryption with Dynamic IV:
public static byte[] encrypt(byte[] plaintext, SecretKey key, byte[] associatedData) throws Exception {
    byte[] iv = new byte[12]; // 96-bit IV recommended by NIST SP 800-38D
    SecureRandom.getInstanceStrong().nextBytes(iv);

    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    GCMParameterSpec spec = new GCMParameterSpec(128, iv); // 128-bit authentication tag
    cipher.init(Cipher.ENCRYPT_MODE, key, spec);

    if (associatedData != null) {
        cipher.updateAAD(associatedData); // Authenticates metadata without encrypting it!
    }
    byte[] ciphertext = cipher.doFinal(plaintext);

    // Pack IV + Ciphertext into single byte array:
    ByteBuffer byteBuffer = ByteBuffer.allocate(iv.length + ciphertext.length);
    byteBuffer.put(iv);
    byteBuffer.put(ciphertext);
    return byteBuffer.array();
}
```

#### Follow-Up Trap Question & Winning Answer
- **Trap:** "If 96-bit IVs are randomly generated, when does the Birthday Paradox make collisions likely?"
- **Winning Answer:** By the Birthday Bound, generating $2^{48}$ random IVs with the same key gives a $50\%$ probability of collision. Therefore, NIST SP 800-38D mandates that a single AES-GCM key must never be used to encrypt more than $2^{32}$ (approx. 4.2 billion) messages with random IVs. For high-volume streaming, rotate keys proactively or use a 64-bit deterministic invocation counter concatenated with a 32-bit device salt.

### Scenario 2: AES-ECB vs AES-CBC vs AES-GCM (The "ECB Penguin" Pattern Leakage)
**Interviewer Evaluation:** Tests understanding of block cipher modes, initialization vectors, pattern leakage, and ciphertext tampering.

#### Technical Deep Dive
- **Electronic Codebook (ECB - `AES/ECB/PKCS5Padding`)**:
  - **FATAL IN PRODUCTION**: Encrypts each 16-byte block independently with the same key.
  - Identical plaintext blocks produce identical ciphertext blocks.
  - The famous **ECB Penguin**: Encrypting an image in ECB mode reveals the clear visual outline and patterns of the image in the encrypted output!
- **Cipher Block Chaining (CBC - `AES/CBC/PKCS5Padding`)**:
  - XORs each plaintext block with the previous ciphertext block before encryption. Requires unpredictable IV.
  - **Vulnerable to Padding Oracle Attacks (BEAST, POODLE)**: CBC does NOT authenticate the ciphertext; an attacker modifying bytes can decrypt data through padding error side-channels.
- **Galois/Counter Mode (GCM - `AES/GCM/NoPadding`)**:
  - **Authenticated Encryption with Associated Data (AEAD)**.
  - Encrypts and authenticates in a single pass. Any modification to the ciphertext, IV, or Additional Authenticated Data (AAD) causes `AEADBadTagException`, stopping tampering attacks instantly.

### Scenario 3: ChaCha20-Poly1305 vs AES-256-GCM: Mobile & Constant-Time Security
**Interviewer Evaluation:** Assesses hardware instruction acceleration (AES-NI) vs software constant-time stream ciphers.

#### Technical Deep Dive
- **AES-GCM**: Requires dedicated CPU hardware instructions (`AES-NI` and `CLMUL` for GHASH). On x86_64 servers with AES-NI, AES-GCM executes at $> 4\text{ GB/sec}$. However, on low-power IoT devices, smart TVs, or older ARM processors lacking AES hardware instructions, AES software implementations use lookup tables (`T-tables`) that are vulnerable to **cache-timing attacks**!
- **ChaCha20-Poly1305 (RFC 8439 - Java 11+)**:
  - 256-bit stream cipher (ChaCha20) coupled with a Poly1305 MAC authenticator.
  - Built purely on ARX operations: **Addition, Rotation, XOR** on 32-bit registers.
  - **Naturally Constant-Time**: Does not perform memory lookups based on secret keys. Zero cache-timing attack vulnerability.
  - Dominates on mobile devices (e.g. Google Android defaults to ChaCha20 for TLS when mobile chips lack AES-NI).

### Scenario 4: Associated Authenticated Data (AAD) in Multi-Tenant Architectures
**Interviewer Evaluation:** Evaluates preventing ciphertext injection across tenant boundaries.

#### Technical Deep Dive
In multi-tenant SaaS, an attacker who obtains a valid encrypted credit card payload from `Tenant A` might inject it into `Tenant B`'s profile table. If only the ciphertext is verified, `Tenant B` successfully decrypts `Tenant A`'s card!
- **The Defense (AAD Binding)**:
  ```java
  cipher.updateAAD(tenantId.getBytes(StandardCharsets.UTF_8));
  ```
  The tenant ID is not encrypted (it remains plaintext in database metadata), but it is cryptographically incorporated into the GCM GHASH authentication tag. Attempting to decrypt the ciphertext under a different `tenantId` throws `AEADBadTagException` immediately.

### Scenario 5: Block Cipher Padding Oracle Attacks on AES-CBC
**Interviewer Evaluation:** Tests understanding of padding schemes (PKCS#7) and chosen-ciphertext side-channels.

#### Technical Deep Dive
In AES-CBC, if a server returns different HTTP responses for:
1. `Invalid Padding Error` vs
2. `Invalid MAC / Decryption Failure`
An attacker can send crafted ciphertexts, alter the last byte of ciphertext block $C_{i-1}$, and determine the exact padding byte decrypted in $C_i$. Iterating over 256 possibilities reveals the plaintext byte without knowing the AES key! This vulnerability broke SSL 3.0 (POODLE) and TLS 1.0 (BEAST). AEAD ciphers (GCM) eliminate padding oracles because they use NoPadding and authenticate the ciphertext before decryption.

### Scenario 6: Zero-Allocation Streaming Cipher Streams (`CipherInputStream`)
**Interviewer Evaluation:** Assesses memory efficiency and stream encryption on multi-gigabyte files.

#### Technical Deep Dive
Encrypting a 5GB file by loading it into a `byte[]` crashes the JVM with `OutOfMemoryError: Java heap space`.
```java
// Production Streaming Encryption using Chunking
public static void encryptFile(InputStream in, OutputStream out, SecretKey key) throws Exception {
    byte[] iv = new byte[12];
    new SecureRandom().nextBytes(iv);
    out.write(iv); // Write public IV first

    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));

    byte[] buffer = new byte[64 * 1024]; // 64 KB buffer
    int bytesRead;
    while ((bytesRead = in.read(buffer)) != -1) {
        byte[] output = cipher.update(buffer, 0, bytesRead);
        if (output != null) out.write(output);
    }
    byte[] finalBlock = cipher.doFinal(); // Writes final block + 16-byte GHASH tag!
    if (finalBlock != null) out.write(finalBlock);
}
```

# Layer 2: Asymmetric Cryptography, ECC & Digital Signatures

### Scenario 7: Asymmetric Signatures: RSA-4096 vs Ed25519 (EdDSA)
**Interviewer Evaluation:** Assesses modern elliptic curve cryptography, Schnorr signatures, constant-time execution, and legacy RSA performance trade-offs.

#### Technical Deep Dive
1. **RSA-4096**:
   - Based on prime factorization. Requires huge 4096-bit keys for 128-bit security equivalent.
   - Extremely slow key generation and high CPU cost during signing.
   - Must use **RSA-PSS (Probabilistic Signature Scheme)**; PKCS#1 v1.5 padding is vulnerable to Bleichenbacher's attack.
2. **Ed25519 (RFC 8032 - Java 15+)**:
   - Twisted Edwards Curve (Curve25519) over a prime field.
   - 32-byte public key and 64-byte signature with 128-bit security.
   - **Naturally Constant-Time**: Arithmetic on Curve25519 is immune to cache-timing attacks without software blinding tricks.
   - **Blazing Speed**: Generates signatures $15\times$ faster than RSA-4096 with zero memory overhead.

### Scenario 8: The Fatal ECDSA Nonce $k$ Reuse Vulnerability (The Sony PS3 Hack)
**Interviewer Evaluation:** Mathematical proof of how repeating a random nonce $k$ leaks the private key in ECDSA.

#### Mathematical Deep Dive
In ECDSA, a signature is a pair $(r, s)$:
$$r = (k \cdot G)_x \pmod n$$
$$s = k^{-1}(z + r \cdot d) \pmod n$$
where $z$ is the message hash, $k$ is a per-signature random nonce, and $d$ is the secret private key.
If two different messages $z_1$ and $z_2$ are signed with the **same nonce $k$**:
1. The $r$ value is identical for both signatures because $r$ depends only on $k$!
2. An observer subtracts the two equations:
   $$s_1 - s_2 = k^{-1}(z_1 - z_2) \pmod n \implies k = \frac{z_1 - z_2}{s_1 - s_2} \pmod n$$
3. Once $k$ is calculated, the private key $d$ is computed directly:
   $$d = \frac{s_1 \cdot k - z_1}{r} \pmod n$$
This exact flaw allowed hackers to extract Sony's root private key from the PlayStation 3!
- **The Defense**: Always use deterministic nonce generation (**RFC 6979**) or **Ed25519**, where $k = \text{SHA-512}(\text{privateKey} \parallel \text{message})$.

### Scenario 9: RSA-OAEP vs PKCS#1 v1.5 Encryption & Bleichenbacher's Attack
**Interviewer Evaluation:** Evaluates chosen-ciphertext attacks on asymmetric padding schemes.

#### Technical Deep Dive
Bleichenbacher's Million Message attack exploits PKCS#1 v1.5 padding:
- A valid PKCS#1 v1.5 block starts with bytes `0x00 0x02`.
- When an altered ciphertext is sent, a server returning different error messages (or varying response times) leaks whether the decrypted block had valid padding.
- Over 1,000,000 requests, the attacker iteratively reconstructs the plaintext.
- **The Defense**: Use **Optimal Asymmetric Encryption Padding (RSA-OAEP)** with SHA-256 and MGF1. OAEP uses Feistel networks and cryptographic hashes to guarantee chosen-ciphertext security (IND-CCA2).

### Scenario 10: Curve Topologies: Weierstrass vs Montgomery vs Edwards
**Interviewer Evaluation:** Assesses architectural understanding of curve mathematics and equation types.

#### Technical Deep Dive
- **Short Weierstrass Curves (`secp256r1` / NIST P-256)**:
  $$y^2 = x^3 + ax + b$$
  Requires exceptional point checks to prevent division-by-zero during point addition; vulnerable to side-channel attacks if not carefully implemented.
- **Montgomery Curves (`X25519`)**:
  $$B y^2 = x^3 + A x^2 + x$$
  Allows the "Montgomery Ladder" algorithm: scalar point multiplication using only the $x$-coordinate, naturally constant-time. Ideal for Diffie-Hellman (ECDH) key agreement.
- **Twisted Edwards Curves (`Ed25519`)**:
  $$a x^2 + y^2 = 1 + d x^2 y^2$$
  Point addition formulas are **complete**: they work for all pairs of points without special cases or exceptions. Highly resilient against side-channel attacks; ideal for digital signatures (EdDSA).

### Scenario 11: Diffie-Hellman & Ephemeral ECDHE Key Exchange Mechanics
**Interviewer Evaluation:** Assesses non-interactive key agreement and Perfect Forward Secrecy.

#### Technical Deep Dive
1. Alice generates private scalar $a$, computes public point $A = a \cdot G$.
2. Bob generates private scalar $b$, computes public point $B = b \cdot G$.
3. They exchange $A$ and $B$ over the public network.
4. Alice computes shared secret: $S = a \cdot B = a \cdot (b \cdot G)$.
5. Bob computes shared secret: $S = b \cdot A = b \cdot (a \cdot G)$.
6. An eavesdropper sees only $A$ and $B$, but cannot compute $S$ without solving the Elliptic Curve Discrete Logarithm Problem!
- **Ephemeral (ECDHE)**: Fresh scalars $a$ and $b$ are discarded immediately after computing the session key, guaranteeing **Perfect Forward Secrecy (PFS)**.

### Scenario 12: Post-Quantum Cryptography: NIST FIPS 203 ML-KEM & FIPS 204 ML-DSA
**Interviewer Evaluation:** Evaluates preparedness for quantum cryptanalysis (Shor's Algorithm).

#### Technical Deep Dive
Quantum computers running Shor's algorithm solve prime factorization and discrete logarithms in polynomial time, completely destroying RSA, ECC, and Diffie-Hellman.
NIST finalized 3 Post-Quantum standards:
1. **ML-KEM (FIPS 203 - CRYSTALS-Kyber)**: Based on the Module Learning With Errors (M-LWE) lattice problem. Fast key encapsulation mechanism for TLS handshakes.
2. **ML-DSA (FIPS 204 - CRYSTALS-Dilithium)**: Lattice-based digital signature standard for certificates and signing.
3. **SLH-DSA (FIPS 205 - SPHINCS+)**: Stateless hash-based signatures providing a fallback if lattice math is ever compromised.

### Scenario 13: Hybrid Classical + Post-Quantum Key Exchange in TLS 1.3
**Interviewer Evaluation:** Tests understanding of real-world quantum migration strategies.

#### Technical Deep Dive
Current enterprise networks cannot immediately switch 100% to PQC because new algorithms have not undergone 30 years of cryptanalysis.
**The Solution: Hybrid Key Exchange (`X25519Kyber768Draft00`)**:
- Client and server compute **both** an X25519 secret and an ML-KEM-768 secret.
- The two secrets are concatenated and fed into HKDF:
  $$\text{SharedSecret} = \text{HKDF}(\text{Secret}_{\text{X25519}} \parallel \text{Secret}_{\text{Kyber768}})$$
- **Security Guarantee**: An attacker must break **BOTH** the elliptic curve and the lattice problem to decrypt the communication!

# Layer 3: Cryptographic Hashing, MACs, KDFs & Password Security

### Scenario 14: Password Hashing: Why Argon2id Beats BCrypt, SCrypt and PBKDF2
**Interviewer Evaluation:** Assesses hardware-resistance against GPU/ASIC cracking, memory-hard hashing functions, and Spring Security `PasswordEncoder` configurations.

#### Technical Deep Dive
- **PBKDF2 (CPU-hard only)**: Requires virtually zero memory. An attacker on a cluster of RTX 4090 GPUs computes billions of PBKDF2 hashes per second at negligible cost.
- **BCrypt (Eksblowfish)**: Requires 4KB of RAM. FPGAs and custom ASIC rigs easily place hundreds of 4KB SRAM instances on a single chip to crack passwords in parallel.
- **Argon2id (Winner of Password Hashing Competition)**:
  - **Memory-Hard**: Fills a configurable memory block (e.g. 64MB per hash) with pseudo-random lookups.
  - GPUs and ASICs have thousands of compute cores but very little memory per core. Filling 64MB of RAM per thread forces GPUs to bottleneck on memory bus bandwidth, making mass brute-force economically unfeasible!
  - `Argon2id` combines `Argon2i` (side-channel resistance) and `Argon2d` (GPU resistance).

---

### Scenario 15: Merkle-Damgård Construction & Length Extension Attacks on SHA-256
**Interviewer Evaluation:** Explains why `H(secret || message)` is catastrophically broken for MACs.

#### Technical Deep Dive
SHA-256 uses the Merkle-Damgård construction: the hash output is simply the internal state after processing the last block.
If an API verifies requests using a naive hash:
$$\text{Signature} = \text{SHA-256}(\text{Secret} \parallel \text{OriginalMessage})$$
An attacker who knows $\text{OriginalMessage}$ and $\text{Signature}$ can append arbitrary data:
$$\text{ForgedMessage} = \text{OriginalMessage} \parallel \text{Padding} \parallel \text{MaliciousCommand}$$
and compute the valid signature **without ever knowing the secret key** by initializing SHA-256 with the original signature as its internal state (**Length Extension Attack**)!
- **The Defense**: Always use **HMAC-SHA256**, which uses nested hashing: $\text{HMAC}(K, m) = H((K \oplus \text{opad}) \parallel H((K \oplus \text{ipad}) \parallel m))$.

---

### Scenario 16: SHA-3 (Keccak) Sponge Construction & Immunity to Length Extension
**Interviewer Evaluation:** Tests structural differences between SHA-2 and SHA-3.

#### Technical Deep Dive
SHA-3 uses the **Sponge Construction** with the Keccak permutation function:
1. **Absorbing Phase**: Message blocks are XORed into a subset of the internal state (the bitrate $r$), followed by state permutations.
2. **Squeezing Phase**: Output hash bytes are extracted from the bitrate.
Because the capacity $c$ of the internal state is kept private and never exported in the output hash, an attacker cannot reconstruct the full state to extend the message. SHA-3 is **naturally immune to length extension attacks**.

### Scenario 17: HMAC-SHA256 vs Plain Hashing for Webhook Authentication
**Interviewer Evaluation:** Assesses symmetric signature verification in distributed architectures.

#### Technical Deep Dive
Webhooks (e.g. Stripe, GitHub) transmit signatures in HTTP headers (`X-Hub-Signature-256`):
```java
public boolean verifyWebhook(byte[] payload, String headerSig, byte[] secretKey) throws Exception {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secretKey, "HmacSHA256"));
    byte[] expectedSig = mac.doFinal(payload);

    byte[] clientSig = HexFormat.of().parseHex(headerSig);
    return MessageDigest.isEqual(expectedSig, clientSig); // Constant-time verification!
}
```

### Scenario 18: Defending against Timing Attacks: Constant-Time Equality (`MessageDigest.isEqual`)
**Interviewer Evaluation:** Tests understanding of CPU branch predictors, early-exit loops, and remote timing side-channels.

#### Technical Deep Dive
- `String.equals()` or `Arrays.equals()`: Terminates on the first mismatched character.
  - Byte 0 mismatch $\to 1.00\text{ ms}$.
  - Byte 0 match, Byte 1 mismatch $\to 1.02\text{ ms}$.
  - An attacker over 100,000 requests measures latency to deduce valid tokens byte-by-byte!
- `MessageDigest.isEqual()`: Evaluates all bytes with bitwise XOR without branching. Execution time is strictly constant regardless of where mismatches occur.

### Scenario 19: HKDF (RFC 5869 Extract-and-Expand Key Derivation)
**Interviewer Evaluation:** Evaluates deriving cryptographically independent keys from a single master secret.

#### Technical Deep Dive
HKDF operates in two steps:
1. **Extract**: Condenses input key material (IKM) and a random salt into a pseudorandom key (PRK) using HMAC:
   $$\text{PRK} = \text{HMAC-Hash}(\text{Salt}, \text{IKM})$$
2. **Expand**: Generates multiple cryptographically independent subkeys of desired lengths for distinct contexts (e.g. encryption key, MAC key, IV):
   $$\text{OKM} = \text{HMAC-Hash}(\text{PRK}, \text{info} \parallel 0x01)$$
Mandated in TLS 1.3 to derive handshake and application keys.

# Layer 4: PKI, X.509 Certificates, CA Hierarchies & KeyStores

### Scenario 20: Anatomy of an X.509 Certificate: SAN vs Deprecated Common Name (CN)
**Interviewer Evaluation:** Assesses modern certificate validation standards (RFC 6125).

#### Technical Deep Dive
- **Common Name (CN)**: Originally placed in the Subject field (`CN=api.example.com`). It is strictly deprecated by modern TLS clients because it cannot represent multiple domain names, IP addresses, or wildcards cleanly.
- **Subject Alternative Name (SAN)**: An X.509 extension (`DNS:api.example.com`, `DNS:*.internal.net`, `IP:10.0.1.50`). Modern browsers and Java TLS engines **completely ignore the CN if SAN is present**, and reject certificates that lack a SAN extension.

### Scenario 21: PKIX Certificate Path Validation & Trust Chain Traversal
**Interviewer Evaluation:** Evaluates root store validation, intermediate CA chaining, and expiry checks.

#### Technical Deep Dive
When a client receives a leaf certificate:
1. Checks date validity: $\text{NotBefore} \le \text{CurrentTime} \le \text{NotAfter}$.
2. Validates signature on leaf using public key of Intermediate CA.
3. Checks `BasicConstraints`: Intermediate CA must have `CA:TRUE` and comply with `pathLenConstraint`.
4. Traverses up the chain until reaching a self-signed **Root Certificate** present in the local TrustStore (`cacerts`).
5. If any link in the chain is missing, expired, or untrusted, throws `SSLHandshakeException: PKIX path building failed`.

### Scenario 22: Certificate Signing Request (CSR) Generation & Private Key Isolation
**Interviewer Evaluation:** Assesses operational security when procuring digital certificates.

#### Technical Deep Dive
> [!IMPORTANT]
> The private key MUST NEVER leave the server where it was generated!
1. Server generates private key locally:
   `openssl ecparam -name prime256v1 -genkey -noout -out server.key`
2. Server generates CSR containing its public key and domain identity, signed by its private key:
   `openssl req -new -key server.key -out server.csr`
3. The CSR is sent to the Certificate Authority (DigiCert, Let's Encrypt).
4. The CA verifies domain ownership and returns the signed certificate chain.

### Scenario 23: Certificate Revocation: CRL vs OCSP vs OCSP Stapling
**Interviewer Evaluation:** Assesses real-time certificate status checking and latency optimization.

#### Technical Deep Dive
- **CRL (Certificate Revocation List)**: Downloadable list of revoked cert serial numbers. Files grow to dozens of megabytes; updates are delayed by hours or days.
- **OCSP (Online Certificate Status Protocol)**: Real-time query to CA server. Adds 100ms latency to every TLS handshake and leaks user browsing privacy to the CA.
- **OCSP Stapling (RFC 6066)**: The web server periodically fetches and caches the signed OCSP response from the CA and "staples" it to the certificate during the TLS handshake. The client validates the timestamped CA signature instantly without contacting any external server.

---

### Scenario 24: Java KeyStore vs TrustStore Architecture
**Interviewer Evaluation:** Clarifies the fundamental difference between identity and trust in Java.

#### Technical Deep Dive
- **`KeyStore`**: Encapsulates **Identity**. Contains the application's private key and public certificate chain. Managed via `KeyManagerFactory`. Used during TLS handshake to prove who the server (or client in mTLS) is.
- **`TrustStore`**: Encapsulates **Trust**. Contains trusted root Certificate Authority (CA) certificates. Managed via `TrustManagerFactory`. Used to verify incoming remote certificates.

---

### Scenario 25: KeyStore Formats: PKCS12 vs Legacy JKS vs PKCS11 HSM
**Interviewer Evaluation:** Tests storage formats, compliance standards, and hardware integration.

#### Technical Deep Dive
- **JKS (Java KeyStore)**: Proprietary to Sun/Oracle. Deprecated since Java 9. Weak integrity algorithms.
- **PKCS12 (`.p12` / `.pfx`)**: Open, international industry standard (RFC 7292). Interoperable with OpenSSL, Windows, and Linux. Default format in modern Java.
- **PKCS11**: Hardware Security Module (HSM) bridge. Private keys reside physically inside tamper-resistant hardware (YubiKey, AWS CloudHSM); cryptographic operations execute on the hardware chip so the private key is **never exposed in JVM memory**.

# Layer 5: SSL/TLS 1.2/1.3, mTLS & Network Security Protocols

---

### Scenario 27: TLS 1.2 (2-RTT) vs TLS 1.3 (1-RTT) Handshake Sequence
**Interviewer Evaluation:** Evaluates low-level network packet exchange and handshake latency optimization.

#### Technical Deep Dive
- **TLS 1.2 Handshake (2 Full Round Trips - 2-RTT)**:
  1. `ClientHello` (lists supported cipher suites).
  2. `ServerHello` + `Certificate` + `ServerKeyExchange` (ECDHE parameters).
  3. `ClientKeyExchange` + `ChangeCipherSpec` + `Finished`.
  4. Server sends `ChangeCipherSpec` + `Finished`.
  5. Application Data begins transmission.
- **TLS 1.3 Handshake (1 Round Trip - 1-RTT)**:
  1. `ClientHello` includes a **KeyShare** guess (client sends its ephemeral Diffie-Hellman public key upfront).
  2. Server responds with `ServerHello` + `KeyShare` + `EncryptedExtensions` + `Certificate` + `Finished`.
  3. Application data transmission starts immediately!
  - **Latency Benefit**: Cuts connection setup time in half across high-latency mobile networks.

---

### Scenario 28: Zero-Round-Trip Time (0-RTT) Early Data in TLS 1.3 & Anti-Replay Defenses
**Interviewer Evaluation:** Assesses performance versus replay attack vulnerabilities in TLS 1.3.

#### Technical Deep Dive
In TLS 1.3, clients resuming a session can send data in the very first packet (`0-RTT Early Data`) using a pre-shared key (PSK).
- **The Critical Vulnerability**: 0-RTT data is **not protected against replay attacks**! An eavesdropper who captures the 0-RTT packet can resend it 5,000 times to the server.
- **The Rule**: Only idempotent requests (`GET /index.html`) may be sent via 0-RTT. State-mutating requests (`POST /api/transfer-funds`) must never be allowed in 0-RTT early data.

---

### Scenario 29: Perfect Forward Secrecy (PFS): Why Ephemeral Keys Prevent Historical Decryption
**Interviewer Evaluation:** Tests understanding of static RSA key transport vs ephemeral Diffie-Hellman.

#### Technical Deep Dive
In legacy RSA key exchange (`TLS_RSA_WITH_AES_128_CBC_SHA`), the client encrypts the pre-master secret using the server's static public key.
- If an intelligence agency records encrypted traffic for 10 years, and eventually obtains the server's private key (via court order, employee theft, or server decommission), they can decrypt **every recorded session from the past 10 years**!
- With **PFS (ECDHE)**, the private keys used to compute the session key exist only in volatile RAM for milliseconds and are destroyed as soon as the session begins. Leaking the server's long-term certificate private key in the future cannot decrypt past traffic.

### Scenario 30: Mutual TLS (mTLS) Zero-Trust Handshake & Client Certificate Verification
**Interviewer Evaluation:** Assesses bidirectional identity verification in microservice service meshes.

#### Technical Deep Dive
```
Client                                                 Server
  │                                                      │
  ├── ClientHello ──────────────────────────────────────>│
  │<── ServerHello + Server Certificate ─────────────────┤
  │<── CertificateRequest (Demands Client Identity!) ────┤
  │                                                      │
  ├── Client Certificate ───────────────────────────────>│
```

The server validates the client certificate against its internal `TrustStore`. The client proves it owns the corresponding private key by signing the handshake transcript in `CertificateVerify`.

### Scenario 31: Disabling Insecure Legacy Ciphers & Protocol Downgrade Defense (SCSV)
**Interviewer Evaluation:** Evaluates protecting systems against MITM downgrade attacks.

#### Technical Deep Dive
An active Man-in-the-Middle attacker can tamper with `ClientHello` packets to pretend the client only supports SSL 3.0, forcing the server to downgrade to an insecure protocol (**Downgrade Attack**).
- **The Defense**:
  1. Disable SSL 2.0, SSL 3.0, TLS 1.0, and TLS 1.1 on all servers.
  2. Implement `TLS_FALLBACK_SCSV` (Signaling Cipher Suite Value, RFC 7507), which alerts the server if a client is attempting an unnecessary downgrade.

### Scenario 33: Custom `SSLContext` & Connection Pools in Spring `RestClient` / `WebClient`
**Interviewer Evaluation:** Demonstrates configuring secure outbound HTTP clients with custom truststores.

#### Technical Deep Dive
```java
@Configuration
public class SecureRestClientConfig {

    @Bean
    public RestClient restClient(
        @Value("${client.ssl.trust-store}") Resource trustStoreResource,
        @Value("${client.ssl.trust-store-password}") String password
    ) throws Exception {
        KeyStore trustStore = KeyStore.getInstance("PKCS12");
        try (InputStream is = trustStoreResource.getInputStream()) {
            trustStore.load(is, password.toCharArray());
        }

        SSLContext sslContext = SSLContextBuilder.create()
            .loadTrustMaterial(trustStore, null)
            .build();

        HttpClient httpClient = HttpClients.custom()
            .setConnectionManager(
                PoolingHttpClientConnectionManagerBuilder.create()
                    .setSSLSocketFactory(SSLConnectionSocketFactoryBuilder.create()
                        .setSslContext(sslContext)
                        .build())
                    .build())
            .build();

        return RestClient.builder()
            .requestFactory(new HttpComponentsClientHttpRequestFactory(httpClient))
            .build();
    }
}
```

### Scenario 35: Host Key Verification & `~/.ssh/known_hosts` (Preventing MITM)
**Interviewer Evaluation:** Assesses trust-on-first-use (TOFU) mechanics and preventing active interception.

#### Technical Deep Dive
When connecting to a server for the first time:
- The server sends its public host key fingerprint.
- The user accepts, and SSH appends it to `~/.ssh/known_hosts`.
- On future connections, if the presented host key does not match `known_hosts`, SSH aborts connection with:
  `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED! POSSIBLE DNS SPOOFING ATTACK!`
This prevents active Man-in-the-Middle attackers from intercepting SSH sessions.

---

### Scenario 36: SSH Public Key Authentication Challenge (`authorized_keys`)
**Interviewer Evaluation:** Step-by-step cryptographic protocol trace of passwordless SSH login.

#### Technical Deep Dive
1. Client sends request to authenticate with key identifier (`id_ed25519.pub`).
2. Server checks if the public key exists in `~/.ssh/authorized_keys`.
3. Server generates a random cryptographic nonce and sends it to the client.
4. Client signs the challenge using its local private key (`id_ed25519`) and returns the signature.
5. Server verifies the signature using the stored public key. If valid, authentication succeeds!
- **Key Insight**: The client private key never leaves the client machine.

---

### Scenario 37: Modern SSH Key Algorithms: `ssh-ed25519` vs `ecdsa` vs `ssh-rsa`
**Interviewer Evaluation:** Assesses key configuration and deprecation lifecycles in OpenSSH.

#### Technical Deep Dive
- `ssh-rsa`: Uses SHA-1 signatures. **Banned in modern OpenSSH (8.8+)** due to practical SHA-1 collision attacks (SHAttered).
- `ecdsa-sha2-nistp256`: Vulnerable to private key recovery if the client's RNG has subtle biases (Sony PS3 flaw).
- `ssh-ed25519`: **Recommended Standard**. Deterministic nonces, 256-bit key size, immune to cache-timing side-channels, fast handshake.

---

### Scenario 38: SSH Port Forwarding Mechanics: Local (`-L`), Remote (`-R`), Dynamic (`-D`)
**Interviewer Evaluation:** Evaluates secure tunneling, bastion hosts, and SOCKS5 proxies.

#### Technical Deep Dive
- **Local Port Forwarding (`ssh -L 5432:db-internal.vpc:5432 user@bastion`)**:
  Opens port 5432 on localhost; forwards traffic through the encrypted SSH tunnel to `db-internal.vpc:5432`.
- **Remote Port Forwarding (`ssh -R 8080:localhost:3000 user@cloud-vps`)**:
  Opens port 8080 on the remote cloud server; forwards incoming internet traffic back to local port 3000 (similar to ngrok).
- **Dynamic SOCKS Proxy (`ssh -D 1080 user@bastion`)**:
  Turns the SSH connection into a full SOCKS5 proxy on port 1080 for arbitrary browser traffic routing.

### Scenario 39: War Room: The `TrustAllManager` Catastrophe Shipped to Production
**Interviewer Evaluation:** Analyzes critical developer shortcuts and Man-in-the-Middle exposure.

### Scenario 40: War Room: Expired Intermediate CA Certificate Microservice Partition
**Interviewer Evaluation:** Diagnoses cascading microservice mesh failure due to intermediate expiration.

#### Production Incident
At 08:00 UTC, all Spring Boot microservices threw `SSLHandshakeException: PKIX path validation failed`. The root CA was valid for another 10 years.

#### Root Cause
The Intermediate Issuing CA expired. While the Root CA was valid, PKIX validation walks the entire chain; an expired intermediate breaks the entire chain of trust.

#### Remediation
- Deployed automated certificate monitoring in Prometheus alerting on any cert in the chain with $< 30$ days validity.
- Automated certificate issuance and rolling restarts via HashiCorp Vault PKI.

### Scenario 41: War Room: Remote Timing Side-Channel Token Extraction in Webhooks
**Interviewer Evaluation:** Detects sub-microsecond timing discrepancies leading to HMAC forgery.

#### Production Incident
An external security researcher successfully forged valid HMAC authentication signatures for webhook payloads.

#### Root Cause
The signature validation method used `Arrays.equals()`:
```java
if (Arrays.equals(expectedHmac, receivedHmac)) { ... }
```
The researcher sent millions of requests, measuring response latency distributions to guess signature bytes one-by-one.

#### Remediation
Replaced with `MessageDigest.isEqual(expectedHmac, receivedHmac)` for constant-time evaluation.

### Scenario 42: War Room: The Debian OpenSSL PRNG Predictable Key Disaster (CVE-2008-0166)
**Interviewer Evaluation:** Assesses the danger of tampering with cryptographic entropy sources.

#### Historical Incident
A Debian maintainer removed two lines of uninitialized memory code to eliminate compiler warnings in Valgrind.
This reduced the OpenSSL PRNG seed space to only **$2^{15} = 32,768$ possible keys**! Attackers precomputed every possible SSH and SSL key in minutes, compromising millions of servers globally.

### Scenario 43: War Room: Plaintext Password Exposure via JVM String Heap Dumps
**Interviewer Evaluation:** Explains memory persistence of immutable `String` objects.

#### Production Incident
An attacker gained read access to a production crash heap dump (`.hprof`) and extracted thousands of plaintext database passwords and API keys.

#### Root Cause
Passwords were read as `String` objects, interned, and retained in JVM Eden/Tenured space indefinitely.

#### Remediation
Read passwords strictly into `char[]` and invoke `Arrays.fill(passwordChars, ' ')` immediately after authentication.

### Scenario 44: War Room: The Heartbleed OpenSSL Buffer Over-Read

#### Historical Incident

### Scenario 45: War Room: Static AES-GCM IV Recovering Database Social Security Numbers

# Layer 8: Beginner Mistakes, Anti-Patterns & Master Decision Matrix

---

### Scenario 46: Anti-Pattern: Defaulting to `Cipher.getInstance("AES")`
**Anti-Pattern:** Defaults to `AES/ECB/PKCS5Padding`. Identical plaintext blocks produce identical ciphertext blocks, leaking structural data.
**Fix:** Always specify full transformation: `Cipher.getInstance("AES/GCM/NoPadding")`.

---

### Scenario 47: Anti-Pattern: Disabling Hostname Verification
**Anti-Pattern:** `HttpsURLConnection.setDefaultHostnameVerifier((hostname, session) -> true);`
Allows an attacker with a valid cert for `evil.com` to intercept traffic intended for `bank.com`!

---

### Scenario 48: Anti-Pattern: Sending Raw Multi-Megabyte Payloads to Cloud KMS
**Anti-Pattern:** Uploading 100MB files to AWS KMS / Vault `Encrypt` API. Exceeds API limits (4KB) and creates network bottlenecks.
**Fix:** Use **Envelope Encryption**: generate a local 32-byte Data Encryption Key (DEK), encrypt locally with AES-GCM, and encrypt only the DEK with KMS.

---

### Scenario 49: The 10 Inviolable Commandments of Enterprise Cryptography

1. **Never roll your own crypto**: Always use standardized algorithms and libraries (JCA, Bouncy Castle).
2. **Never use AES-ECB**: Mandate AES-GCM or ChaCha20-Poly1305 (AEAD).
3. **Never reuse an IV in AES-GCM**: Generate 12 fresh random bytes per write.
4. **Use `MessageDigest.isEqual()`**: Eliminate remote timing attacks on MACs and tokens.
5. **Never store passwords with SHA-256 or MD5**: Use Argon2id or BCrypt.
6. **Wipe secrets from RAM**: Use `char[]` or `byte[]` and call `Arrays.fill(..., (byte)0)`.
7. **Always enforce SAN in X.509 certificates**: Common Name (CN) is deprecated.
8. **Adopt Perfect Forward Secrecy (PFS)**: Require ephemeral key exchange (ECDHE).
9. **Never ship dummy `TrustManager` instances to production**: Enforce strict CA chain verification.
10. **Use modern SSH keys (`ssh-ed25519`)**: Deprecate `ssh-rsa` (SHA-1).
